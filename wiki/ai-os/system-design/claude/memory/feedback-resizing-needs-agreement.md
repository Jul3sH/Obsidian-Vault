**Two rules, one correction.**

1. **Never change a `t-shirt` size or WSJF score without asking Julian first.** Sizing is his judgement call, not a derived output. If a scope change makes an existing size stale, say so, flag the field as stale with a date, and put the re-size in Next Actions as a thing to do *with him*. Do not write a new number and report it as done.
2. **Size on the work REMAINING, not the work listed.** When scope is extended into a project that already has completed work, the size covers what is left to do. Counting the full activity list counts work Julian has already finished.

**Why:** on 28 Aug 2026, extending the UK Relocation Project into execution scope, I wrote a ~50-row activity register, counted the rows, and re-scored the project S → L and WSJF 6.0 → 2.6 in the same operation. Both moves were wrong. The register included an unknown amount of already-completed work (Julian had said the move was underway), so the count was not the remaining job; and he had never agreed the number. His words: *"How did you know how much bigger to make the job? ... You should be checking with me before you re-size something."* A fabricated estimate is worse than a stale one, because a stale field flags itself and an invented one does not.

**How to apply:** on any scope extension, produce the scope and mark the size field stale with a date. Establish what is already done first, strip it, then propose a size *as a question*. Only write `t-shirt` / `wsjf` once Julian has agreed. Related: [[feedback-wsjf-double-counting]] (run the Value counterfactual before proposing a Value score), [[feedback-verify-before-writing]].
