# MM: Systems Are Motivation

This is the Systems-as-Motivation mental model: a working operational system (a
tracker, a schedule, a prioritisation process) is not admin overhead, it is the thing
that actually generates the motivation to do the work. It exists because this was a
MISSED lesson: no existing article captured the specific angle that a visible,
working system is itself the fuel. Read it before treating "get the system current"
as a low-value chore to be skipped under time pressure.

**One-liner:** The tracker is not overhead on the work, it is the engine that gets
the work done.

**Reach for it when:** you are deciding whether it is worth the time to keep a
system (tracker, schedule, checklist) current, or tempted to drop a working one for
something new.

## Key Takeaways

- A current, visible system does two things at once: it removes the need to defend
  what you've done, and it motivates you to complete tasks so they can be ticked off
  (a Parkinson's-Law effect running in the helpful direction).
- Getting things done against a structured, prioritised list feels good in a way
  that reorganising the list does not; that feeling is a signal to protect, not
  suppress.
- A system that already works is not a candidate for replacement just because
  something new and shiny turned up. Novelty is not evidence of a better system.
- Building a system is not the same as running it. A system only pays off once it
  is adopted and kept current; a beautifully designed but abandoned tracker produces
  nothing.

## Principles

- **Operational systems in place is an absolute priority, not a nice-to-have.**
  Suffering from not having one running properly is a recoverable, self-inflicted
  cost.
- **A current system provides transparency**, removing the need to justify what you
  have been doing to someone else, and **motivates completion**, because ticking
  something off a visible list is its own reward.
- **Limit organising time.** The good feeling comes from doing items on the list,
  not from reorganising the list; reorganising is procrastination wearing a
  productive disguise.
- **Do not drop a good system for a new one just because it is new.** Novelty is not
  a reason; if the old system is still robust, the "shiny new thing" instinct is the
  thing to be suspicious of, not the old system.

## Guidelines

- When a system starts to feel stale, check whether it has actually stopped working
  or whether the pull is toward the novelty of building something new. Only replace
  it if the first is true.
- Treat "keep the tracker current" as a scheduled task with its own slot, not
  something done only when there is spare time; its payoff (motivation, visibility)
  degrades the moment it goes stale.
- A newly built system is not done when designed. Name an adoption forcing-function
  at creation (a scheduled first use, a trigger, an accountability check) and log it
  in [[systems-register]], or the system is likely to be abandoned unused. See the
  `feedback-build-dont-adopt` memory, mirrored at [[feedback-build-dont-adopt]], for
  the sibling failure this guards against: designing is the reward, running is the
  discipline gap.

## Limitations

This model says a working system generates motivation; it does not say every task
needs a system, and building one for a one-off task is overhead, not leverage. It
also does not resolve which system to build, only that an existing working one
should not be dropped without cause, and that a built system still needs adoption to
pay off.
