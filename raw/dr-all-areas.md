# AI Engineering Patterns Catalog

This catalog surveys nine pattern areas that recur across production AI engineering in 2025-2026, structured to support routing engineering tasks to the right approach. Each area follows a fixed structure: definition, routing triggers, technique taxonomy, concrete examples, anti-patterns, state of practice, and sources.

## AREA 1 — CONTEXT ENGINEERING

### 1. Definition
Context engineering is the discipline of curating and structuring the finite set of tokens fed into an LLM at inference time — not just the initial prompt, but everything competing for the model's limited "attention budget," including retrieved documents, tool outputs, memory, and conversation history. It is distinguished from prompt engineering, which is the narrower craft of wording a single instruction well; context engineering treats the entire, constantly evolving universe of possible information and decides the smallest high-signal subset to include for a given inference step. Practitioners increasingly frame the discipline as an information-flow problem spanning RAG, memory, and compaction rather than a single prompt-authoring task.

### 2. Routing Triggers
Reach for context engineering when a task involves multi-turn or long-running agent sessions that risk exceeding the context window, when the input mixes heterogeneous sources (system instructions, retrieved knowledge, tool outputs, history) that need explicit structuring, or when response quality is degrading due to "context rot" from accumulated, low-signal tokens. It is also the right lens whenever a team is deciding how to structure a system prompt with XML/Markdown sections, or when choosing between stuffing more into context versus retrieving less but more relevant content.

### 3. Technique Taxonomy
- **Structured prompting** — organizing prompts into tagged sections (`<background_information>`, `## Tool guidance`) so the model can parse different information types; used at the authoring stage of any system prompt.
- **Context compaction** — summarizing older conversation turns into a high-fidelity summary once a token threshold is hit, replacing raw history; used for long-running agentic loops (Anthropic's `compact_20260112`, default trigger 150K input tokens).
- **Context editing / tool-result clearing** — server-side clearing of stale tool outputs (`clear_tool_uses_20250919`) rather than summarizing them; used when tool output volume dominates the window rather than dialogue.
- **Hierarchical context structuring** — layering system prompt, top retrieval results, background knowledge, and tool descriptions so the model "sees the most important information first"; used in RAG-heavy applications.
- **Selective/dynamic injection** — LLM-driven routing logic that decides which knowledge fragments to load per query rather than always loading everything; used for variable, query-dependent context needs.
- **RAG vs long-context selection** — choosing retrieval versus loading full documents based on corpus size, update frequency, and need for source attribution; RAG is roughly 1,250x cheaper per query than long-context loading and preferred above roughly 50–200K tokens of corpus, while long context wins for small, stable, cross-document reasoning tasks.
- **Hybrid retrieval + long context** — using RAG to narrow candidates, then long-context reasoning over retrieved passages; the emerging 2026 default rather than treating RAG and long context as exclusive.

### 4. Concrete Examples
Anthropic's Claude Platform ships first-party server-side compaction (`compact_20260112`) and context editing (`clear_tool_uses_20250919`) as production APIs, plus a client-side memory tool (`memory_20250818`). Claude Code and the Claude Agent SDK use `compaction_control` to auto-summarize when token usage crosses a configurable threshold, with prompt caching cutting resummarization cost by roughly 80%. Letta's engineering team draws the explicit conceptual line "RAG is a retrieval pattern, not a memory system," running a layered hybrid architecture combining RAG, compressed observation logs, and live context. Gemini 3 Pro's 2-million-token window and Claude Opus 4.6's 1M-token beta context represent the long-context end of the tradeoff spectrum discussed across 2025-2026 sources.

### 5. Anti-Patterns & Failure Modes
Brute-force stuffing of an entire corpus into context degrades quality via the "lost in the middle" effect and grows compute cost non-linearly. Relying on long context alone for large (>1M token) or frequently updated knowledge bases is both cost-prohibitive and operationally impractical, since filling a 1M window can take roughly 60 seconds per query. Waiting until the window is nearly full to compact, rather than maintaining a running background summary, risks abrupt quality loss right when task complexity is highest. Treating RAG and long context as mutually exclusive rather than complementary is a commonly cited strategic error in 2026 practitioner writing.

### 6. State of Practice
The field matured rapidly through 2025-2026: Anthropic's compaction and context-editing primitives moved from cookbook patterns to GA API features, and the July 2025-era distinction between "prompt engineering" and "context engineering" is now standard vocabulary. Benchmarks such as LaRA (2025) show RAG matching or beating long-context loading for factual Q&A, with long context earning its keep primarily for holistic, cross-document reasoning. This is a mature, actively-evolving area; treat any claim about model context-window size as time-sensitive given rapid 2026 expansions.

## AREA 2 — MEMORY

### 1. Definition
Agent memory is a persistent storage layer that lets an agent retain and act on information across turns and sessions — distinct from context engineering (which manages what's in the current window) and from RAG (which retrieves largely static, pre-existing enterprise knowledge). Memory ends and retrieval begins at the data source: memory processes dynamically generated interaction logs and agent-derived state (preferences, summaries, reflections) to maintain continuity and personalization, while RAG processes static domain documents for factual grounding — the two are complementary layers, not substitutes.

### 2. Routing Triggers
Choose a memory architecture when an agent must persist facts, preferences, or learned behavior across sessions rather than within one; when conversation history alone would exceed context limits over many sessions; or when personalization and continuity (not one-off document lookup) are the core requirement. It's also the right pattern when an agent needs to self-manage what it forgets versus retains, rather than relying on an external engineer to prune manually.

### 3. Technique Taxonomy
- **Write-time extraction** — facts are extracted and stored at the moment of interaction (e.g., Mem0's single-pass ADD-only extraction); used when retrieval speed and cost matter more than write-time compute.
- **Query-time retrieval** — memory is searched and assembled only when needed via semantic, keyword, or graph search; used when agents need broad recall without loading everything up front.
- **Core/working memory** — a small, always-in-context block holding identity and key facts (Letta's "core memory"); used for invariant persona/task state.
- **Episodic memory** — records of specific past events/interactions with temporal ordering (conversation logs, tool-call traces); used to recall "what happened, when."
- **Semantic memory** — atemporal declarative facts and relationships (user preferences, entity properties); used for grounding and personalization.
- **Procedural memory** — learned workflows, tool-call sequences, and behavioral heuristics; used so agents reuse successful strategies rather than relearning them.
- **Memory decay/promotion** — overflow from short-term buffers is archived to long-term stores and rehydrated on demand via search; used to keep active context small while retaining unbounded history.
- **Temporal knowledge graphs** — Zep's Graphiti engine models facts with explicit validity windows so agents know when something was true, not just what is true; used where temporal correctness matters (e.g., "what did the user believe last month").

### 4. Concrete Examples
Letta (formerly MemGPT) implements a three-tier hierarchy — core, recall, archival memory — with self-editing memory via tool calls, and shipped skill learning in December 2025 letting agents persist reusable skills from task trajectories. Mem0 reports 92.5–93.4 on LoCoMo/LongMemEval benchmarks using single-pass hierarchical extraction at roughly 6,900 tokens per query, and ships as a managed platform, OSS package, and local memory server for MCP clients like Claude Desktop and Cursor. Zep deprecated its Community Edition in April 2025 in favor of Graphiti, its open-source temporal knowledge-graph engine (Apache-2.0, ~27k GitHub stars), which now powers Zep Cloud. Claude's built-in memory tool (`memory_20250818`, GA) persists notes to files the application stores and Claude reads back just-in-time. Letta's Filesystem approach scored 74.0% on LoCoMo simply by storing conversation histories in files, outperforming several specialized memory libraries — a notable 2025 finding that simple approaches can rival complex ones.

### 5. Anti-Patterns & Failure Modes
Conflating memory with RAG — using a vector store of static documents as if it were an agent's evolving memory — produces stale or irrelevant personalization. Benchmark comparisons between memory vendors are contested: Mem0 and Zep publish substantially different LongMemEval and LoCoMo numbers depending on evaluation methodology and configuration, and independent evaluations (e.g., vectorize.io) sometimes reverse the vendor's own published rankings — treat any single vendor's benchmark claim as marketing-influenced and cross-check. Letting agents self-manage memory without decay policies risks unbounded, low-signal archival growth that later degrades retrieval precision. Persistent memory is also a documented security liability — attackers have exploited cross-session memory as a persistence mechanism for injected instructions, so unused memory features should be disabled.

### 6. State of Practice
The field converged in 2025-2026 on a three-tier episodic/semantic/procedural taxonomy borrowed from cognitive science, now a production consensus rather than an academic curiosity. The Mem0 research paper (ECAI 2025, arXiv:2504.19413) established the first broad head-to-head comparison of ten memory approaches including Zep and full-context baselines. Letta's V1 architecture (October 2025) deprecated older heartbeat/send_message patterns in favor of native model reasoning, reflecting rapid framework churn even within a single vendor. Benchmark contest between Mem0 and Zep is active and unresolved as of mid-2026; independent third-party evaluations diverge from vendor self-reports, so this space should be flagged as contested.

## AREA 3 — TOOLS & MCP

### 1. Definition
Tool design and the Model Context Protocol (MCP) cover how LLM agents discover, call, and are permitted to use external functions and services — MCP specifically is an open, JSON-RPC 2.0-based standard, introduced by Anthropic in November 2024 and donated to the Linux Foundation's Agentic AI Foundation in December 2025, that standardizes agent-to-tool communication so any compliant client can use any compliant server.

### 2. Routing Triggers
Reach for structured tool design when an agent needs deterministic, auditable side effects (database writes, API calls, file operations) rather than free-text generation. Reach for MCP specifically when an agent needs to integrate with third-party or in-house services in a vendor-neutral way, especially across multiple clients (Claude, ChatGPT, Cursor) that shouldn't each need bespoke integration code. Tool discovery/search patterns become relevant once the available tool count grows into the hundreds or thousands and naive listing floods the context window.

### 3. Technique Taxonomy
- **Single-purpose tool design** — one clear job per tool with a descriptive name (e.g., `search_orders` not `do_stuff`); used to avoid model confusion between overlapping tools.
- **Model-facing descriptions** — writing tool descriptions as prompts for the model (stating when to use/not use it) rather than developer documentation; used for every tool exposed to an LLM.
- **Schema typing and validation** — strict JSON Schema typing, enums, and business-rule validation before execution; used to prevent malformed or unsafe calls.
- **Actionable error returns** — structured errors that tell the model how to recover ("call search_orders first") instead of raw stack traces; used to enable self-correction loops.
- **MCP transports** — stdio (local) and Streamable HTTP (remote, replacing SSE in March 2025) for connecting clients to servers; used based on deployment topology.
- **MCP OAuth 2.1 authorization** — resource-server model with Protected Resource Metadata (RFC 9728) and Client ID Metadata Documents (CIMD, Nov 2025) for remote server auth; used whenever an MCP server exposes privileged operations.
- **Semantic/scalable tool discovery** — retrieval-based or hierarchical mechanisms (e.g., experimental DNS-based ToolDNS) to find relevant tools among tens of thousands without O(N) context cost; used at very large tool-catalog scale.
- **Tool permissioning/gating** — exposing the minimum tool surface, gating destructive actions behind confirmation, and rate-limiting; used for any agent with real-world side effects.
- **Structured output / constrained generation** — a reliability layer for tool-calling interfaces spanning three tiers: prompt-only JSON (no guarantee), provider JSON mode (guarantees parseable but not schema-conformant JSON, 8-15% failure rate on complex shapes), and schema-constrained/grammar-based decoding (guarantees ~99.9-100% schema compliance by masking invalid tokens at the sampler); used whenever a tool call's arguments or an agent's final answer must reliably match a fixed shape.

### 4. Concrete Examples
By December 2025, MCP had 97M+ monthly SDK downloads and 10,000+ active public servers per Anthropic's own ecosystem update, spanning Slack, GitHub, Salesforce, Stripe, and Notion integrations. Every major AI platform — Claude, ChatGPT (Apps SDK, April 2025), Gemini (March 2026), Microsoft Copilot, Cursor, Windsurf, Zed — ships native MCP support. Composio offers 1,000+ toolkits and 20,000+ discoverable tools, illustrating the scale problem tool search must solve. The July 28, 2026 spec revision removed the initialize/initialized handshake and session IDs, making MCP stateless at the protocol layer — described by maintainer David Soria Parra as the most substantial change since authorization was added. The academic ToolDNS proposal (2026) benchmarks tool discovery across 33,688 real-world tools spanning MCP, A2A, REST, and Skill protocols. By mid-2026 all three major providers shipped true schema-constrained decoding: OpenAI's `json_schema` with `strict: true`, Anthropic's `output_config`/strict tool use (GA since early 2026, beta since November 2025), and Google Gemini's `responseSchema`/`responseJsonSchema`; local runtimes (llama.cpp, Ollama, vLLM) implement the same guarantee via GBNF grammars or guided-decoding backends like XGrammar.

### 5. Anti-Patterns & Failure Modes
Overlapping or vaguely-named tools cause models to pick the wrong one; the fix is a small, distinct tool surface. Exposing an unbounded number of tools directly in context (rather than using discovery/search) degrades both latency and accuracy — this is the same "lost in the middle" problem seen in context engineering, now applied to tool schemas. Registries are fragmented and self-reported — different MCP directories (Glama, PulseMCP, Smithery) report wildly divergent server counts using different methodologies, so adoption statistics should be treated skeptically and cross-checked. Relying on plain JSON mode in production without schema enforcement is a documented anti-pattern by mid-2026 standards — it guarantees only that output parses, not that it matches the required structure, and OpenAI itself now labels unconstrained JSON mode "legacy."

### 6. State of Practice
MCP is now the de facto standard for agent-to-tool communication, with governance moved to the Linux Foundation and a fast-moving spec cadence (2024-11-05 initial → 2025-03-26 Streamable HTTP → 2025-11-25 OAuth 2.1/CIMD → 2026-07-28 stateless core). Adoption statistics vary by source (41% of surveyed software orgs in limited/broad production per one 2026 survey, versus higher "78% of enterprise teams" claims flagged elsewhere as not fully source-safe), so growth figures should be treated as directionally strong but not precisely reconcilable across reports. Enterprise focus in 2026 has shifted from basic integration toward gateway/registry control planes, structured audit trails, and SSO-integrated auth. Structured output has matured from a significant 2023-2024 pain point into a solved, production-ready capability by 2026, with one caveat noted in research: constrained decoding carries a measured creativity cost (roughly 17% in one study) worth weighing for open-ended generation tasks.

## AREA 4 — EVALS

### 1. Definition
Eval-driven development treats systematic measurement of LLM/agent output quality — via automated assertions, task-level evals, LLM-as-judge scoring, or human review — as a first-class engineering practice, analogous to test-driven development but adapted for probabilistic systems. Product evals (custom, task-specific test suites tied to a real application) are distinct from public benchmarks (generic capability leaderboards); production teams rely primarily on the former.

### 2. Routing Triggers
Reach for eval-driven development whenever a change to a prompt, model, or agent workflow needs to be validated before shipping — i.e., any non-trivial LLM feature in production. Use offline eval frameworks in CI as a pre-deploy gate; use observability platforms once the system is live and needs to be monitored on real traffic; use LLM-as-judge when outputs are open-ended text that can't be checked by exact-match assertions; use human review for high-stakes or ambiguous judgment calls.

### 3. Technique Taxonomy
- **Unit-style assertions** — deterministic checks (regex, schema validation, exact match) on structured or constrained outputs; used for narrow, verifiable tasks.
- **End-to-end task evals** — scoring whether an agent achieved a real task outcome across a full trajectory, not just one output; used for agentic workflows with tool use.
- **LLM-as-judge** — a separate LLM scores outputs against a rubric; used when human-grade judgment is needed at scale but ground truth is not exact-matchable.
- **Human review** — manual annotation/grading, often used to calibrate or validate LLM-as-judge scores; used for high-stakes or hard-to-automate judgment.
- **Regression suites** — versioned datasets run in CI to catch quality regressions across prompt/model changes; used before every deploy.
- **Trace-level / production observability** — capturing full traces across tool calls, retrieval, and multi-step workflows and scoring live traffic continuously; used post-deployment.
- **Red-teaming / adversarial evals** — declarative, multi-model comparison and systematic attempts to break the app before release; used for safety and robustness validation.
- **Synthetic eval-set generation** — using a teacher LLM (ideally from a different model family than the system under test) to generate adversarial and edge-case test inputs at scale where human annotation is prohibitively expensive; used to expand golden sets beyond what manual curation can cover, with strict judge-filtering (threshold 0.8+, 10% human spot-check) since eval sets demand the highest quality bar of any synthetic-data use case.

### 4. Concrete Examples
Braintrust crossed roughly $36M ARR in 2025 with OpenAI, Notion, Vercel, Stripe, Brex, and Airtable as named users, running full-trace scoring via its purpose-built Brainstore database. LangSmith is LangChain's hosted platform for tracing, datasets, and online evals, with the deepest automatic instrumentation for LangChain/LangGraph stacks. Promptfoo is an open-source, config-driven eval and red-teaming harness commonly used as a CI pre-deploy gate, distinct from LangSmith's full-lifecycle observability role. Langfuse (MIT-licensed, self-hostable) and Arize Phoenix serve as open-source alternatives for tracing plus evals. The standard production pattern pairs a code-first framework (DeepEval, promptfoo, RAGAS) for CI gating with an observability platform (LangSmith, Langfuse, Braintrust) for live monitoring. The most effective golden datasets combine human-crafted edge cases, PII-scrubbed real production samples, and synthetic expansions specifically targeting underrepresented scenarios.

### 5. Anti-Patterns & Failure Modes
Relying solely on public benchmarks (MMLU-style leaderboards) to validate a specific product feature is a common and misleading practice — benchmarks measure generic capability, not whether a particular application does its job. Using promptfoo alone, without a production observability layer, leaves teams blind to how the system behaves on live traffic, since promptfoo does not include built-in production monitoring. Skipping trace-level scoring for multi-step agent workflows and only scoring final outputs hides where in a trajectory failures actually occur. Generating synthetic eval data with the same model family used to generate training data (or the model under test) produces eval overfitting — the eval quietly becomes optimistic rather than challenging, and the corrective practice is to use a distinct model family as the judge/generator for eval sets.

### 6. State of Practice
The eval/observability space is commercially active and consolidating: this is a maturing but still-fragmenting category as of 2026, with distinct code-first (CI-gating) and platform (production-monitoring) segments that most serious teams run in tandem. Vendor ARR and adoption figures (e.g., Braintrust's $36M ARR) come from industry reporting rather than audited disclosures and should be treated as approximate. Synthetic data generation methodology matured substantially through 2026, converging on three generation patterns — persona-prompted phrasing, taxonomy-stratified coverage, and evolution-based difficulty escalation (Evol-Instruct) — paired with a filter whose intensity varies by use case: eval sets get the strictest filter (small volume, judge threshold 0.8+), fine-tune sets a mid filter (larger volume, threshold ~0.7), and red-team sets an inverted filter that rejects only unrealistic attacks rather than difficult ones. See Area 8 for a fuller treatment of the production-monitoring/drift-detection layer, which 2026 practitioner sources increasingly treat as distinct from eval-driven development proper.

## AREA 5 — ORCHESTRATION & WORKFLOW ARCHITECTURES

### 1. Definition
Orchestration and workflow architecture concerns how multiple LLM calls or agents are composed to solve a task — spanning the spectrum from workflows (predefined, deterministic control flow) to agents (model-driven, dynamic control flow), and from single-agent to multi-agent systems. Anthropic's foundational framing: workflows have fixed, predictable execution paths, while agentic systems let the model itself decide the sequence of steps and tool calls.

### 2. Routing Triggers
Reach for a workflow (deterministic control flow) when the task decomposes into a known, repeatable sequence of stages (approval chains, compliance checks). Reach for a single agent with tools as the default baseline for any task that fits one context window without needing parallelism. Escalate to multi-agent only after identifying a specific, concrete failure in the single-agent baseline — a context-window limit, a genuine parallelism opportunity, or a need for independent critique — never as a default starting point.

### 3. Technique Taxonomy
- **Prompt chaining / sequential pipeline** — output of step N feeds step N+1, each with a focused prompt; used for naturally ordered stages like draft → critique → refine.
- **Routing / classify-and-act** — classify the input then dispatch to a specialist prompt or agent; used when inputs fall into known categories needing different handling.
- **Parallelization / fan-out and synthesize** — dispatch N independent workers concurrently, then a reducer synthesizes; the "map-reduce for LLMs" pattern, and the shape behind Anthropic's Research system.
- **Sectioning vs voting** — sectioning divides a task into independent parallel chunks; voting runs multiple agents on the same task and takes majority/best answer (generate-and-filter, tournament-style ensembles).
- **Orchestrator-workers (supervisor)** — a lead agent dynamically plans, delegates, and aggregates from specialized subagents; documented in Anthropic's "How we built our multi-agent research system" (March 2025) and used in Claude Code for background subagent search.
- **Generator-verifier / evaluator-optimizer (adversarial verification)** — one agent produces output, another verifies against explicit criteria and loops until acceptable; Anthropic warns it fails when verification criteria are undefined, creating "the illusion of quality control without the substance."
- **Agent teams (persistent workers)** — unlike orchestrator-subagent, workers persist across assignments and accumulate domain knowledge; used for large-scale migrations where familiarity compounds.
- **Message bus / event-driven** — workflow emerges from events rather than a predetermined sequence; used for pipelines like security-alert triage where new capabilities plug in without rewiring.
- **Shared state / blackboard** — no central coordinator; agents read/write a persistent store directly; used for research synthesis where findings should immediately inform others.
- **ReAct and ReWOO** — the foundational reasoning+acting loop, and its variant that plans upfront then executes in parallel; used as base agent-loop patterns underlying most of the above.

### 4. Concrete Examples
Anthropic's multi-agent Research system (Claude Opus 4 lead + Claude Sonnet 4 subagents) beat single-agent Claude Opus by 90.2% on an internal research eval, but consumed roughly 15x the tokens of an ordinary chat versus a single agent's ~4x. LangGraph, the OpenAI Agents SDK, CrewAI, and the Microsoft Agent Framework converged on the same four shapes in 2026 documentation: supervisor/orchestrator-worker, parallel fan-out/fan-in, sequential handoff, and shared-state/swarm. Claude Code itself uses orchestrator-subagent patterns for background codebase search while the main agent continues primary work. Community engineering guides (e.g., enuno/claude-command-and-control) report single-agent-with-skills achieving 35% token reduction versus multi-agent for sequential coding tasks.

### 5. Anti-Patterns & Failure Modes
Defaulting to multi-agent before establishing a single-agent baseline and identifying its concrete failure mode is the most commonly cited anti-pattern across 2026 sources. Multi-agent systems are a poor fit for tasks needing shared context across all agents, heavy step interdependencies, or real-time coordination — most coding tasks fall into this category and are better served by a single agent with longer context. Deep orchestration hierarchies introduce coordination latency without proportional benefit; "over-coordination" is a named failure mode in production guides. Generator-verifier loops implemented without clearly defined verification criteria create false confidence rather than real quality control.

### 6. State of Practice
As of 2026, there is a clear industry consensus that supervisor-plus-parallel-fan-out is the "house pattern" for read-heavy, independent work, while single-agent with long context wins for write-heavy, coupled work — this framing appears consistently across Anthropic, OpenAI, LangChain, and Microsoft's 2026 documentation. Anthropic's own March 2025 multi-agent research write-up remains the most-cited empirical evidence for multi-agent value, though it is over a year old relative to this catalog's date and newer sources increasingly emphasize when NOT to use it.

## AREA 6 — SPEC-DRIVEN DEVELOPMENT

### 1. Definition
Spec-driven development (SDD) treats a written specification — not the code — as the source of truth that AI coding agents implement against, flipping the traditional relationship where specs were scaffolding discarded once "real" coding began; in SDD, specifications become directly executable artifacts that generate implementations.

### 2. Routing Triggers
Reach for spec-driven development when a task is complex enough that jumping straight to code with an AI agent risks scope drift, ambiguous requirements, or unreviewable large diffs. It's the right pattern for greenfield features needing structured requirements traceability, multi-step implementations that benefit from a plan-then-execute gate, or team environments where a human needs to review intent before code is generated.

### 3. Technique Taxonomy
- **Spec-first workflows** — writing a structured spec (requirements, acceptance criteria) before any code generation; used to lock down intent.
- **Plan-then-execute** — decompose the spec into a plan, then tasks, then implementation, with review gates between phases (GitHub Spec Kit's Specify → Plan → Tasks → Implement).
- **EARS notation (acceptance criteria for agents)** — Easy Approach to Requirements Syntax used to generate machine-checkable requirements documents (Amazon Kiro's `requirements.md`); used when acceptance criteria need to be unambiguous enough for an agent to self-verify.
- **Test-first with agents / agent hooks** — automated hooks that run tests as verification gates tied to the spec (Kiro's Agent Hooks); used to enforce that implementation matches the spec before merge.
- **Living vs static specs** — Kiro's specs are bidirectionally updated as code changes; Spec Kit's are static, write-once documents handed to the agent; the choice affects whether specs stay accurate over a project's lifetime.
- **Requirement-to-task traceability** — mapping each generated task back to a specific requirement line, enabling audit of coverage; a differentiator among 2026 tools.

### 4. Concrete Examples
GitHub Spec Kit, open-sourced September 2025, is an MIT-licensed Python CLI supporting 30+ AI coding agents (Claude Code, Copilot, Cursor, Windsurf, Codex CLI) and had accumulated 107,000 GitHub stars by May 2026, running a constitution → specify → plan → tasks → implement loop entirely in plain Markdown. Amazon Kiro is a VS Code fork with spec-driven development built into the IDE itself, generating EARS-notation requirements, a design doc, and a dependency-sequenced task list, backed by Claude Sonnet and Amazon Nova via Bedrock. OpenSpec is named as a lightweight option for "brownfield" projects where a full spec rewrite isn't practical. The category traces its name and much of its early framing to research by John Lam that GitHub built on.

### 5. Anti-Patterns & Failure Modes
Treating a spec as a one-time document with "None (convention)" enforcement — as GitHub Spec Kit currently does — means nothing prevents an agent from silently drifting from the spec during implementation unless a human actively re-reviews. Using a static-spec tool for a fast-moving, iterative codebase risks specs becoming stale relative to the code, unlike living-spec tools such as Kiro. Locking into a proprietary IDE (Kiro/AWS Bedrock) trades portability for tighter spec-to-code integration — a real tradeoff, not simply a downside, but one teams should make deliberately.

### 6. State of Practice
This is a genuinely nascent 2025-2026 category: GitHub Spec Kit launched publicly in late 2025 and reached v0.8.7 only in May 2026, while Kiro remains AWS-specific tooling. No dominant enforcement mechanism has emerged yet — most tools rely on convention and human review rather than automated gating — and this should be flagged as an actively evolving, unsettled area of practice rather than a mature discipline.

## AREA 7 — SECURITY & AGENT IDENTITY

### 1. Definition
This area covers the threat model unique to LLM agents — prompt injection (direct and indirect), tool permissioning and sandboxing, data exfiltration, and MCP supply-chain trust — together with agent identity: the emerging standards for how autonomous agents authenticate, hold workload identity, and act on a user's behalf via delegated authorization.

### 2. Routing Triggers
Apply this pattern area whenever an agent ingests untrusted external content (web pages, documents, emails, third-party API responses), has access to consequential tools (payments, code execution, data deletion, email send), or needs to act with its own credentials rather than borrowing a human's session. It is also the right lens whenever adopting third-party MCP servers, since every external server is a new trust boundary.

### 3. Technique Taxonomy
- **Indirect prompt injection mitigation** — instruction/data separation, provenance tagging, and stripping hidden text (zero-width characters, off-screen elements) from untrusted content before it enters context; used for any agent processing external documents.
- **Least-privilege tool permissioning** — scoping each agent/tool to the minimum required capability (e.g., read-only where write isn't needed); the single most cited mitigation across 2025-2026 security research.
- **Human-in-the-loop approval gates** — mandatory human confirmation before irreversible or high-impact actions (payments, deletions, external sends); used as a backstop when injection succeeds.
- **Sandboxing / process isolation** — running MCP servers or tool executors in isolated containers with restricted OS privileges; used to contain command-injection or RCE-class MCP vulnerabilities.
- **Tool description hash-pinning** — freezing an approved tool's description at review time and requiring re-approval on any change, defending against MCP "rug-pull" attacks.
- **Supply-chain provenance verification** — AI Bill of Materials (AIBOM), signed components, and verified-publisher checks for every MCP server dependency; used to counter trojanized packages.
- **Workload identity (SPIFFE/SVID, WIMSE)** — cryptographically verifiable, short-lived credentials for the agent itself (not a shared secret), answering "who is this agent"; the CNCF-graduated consensus mechanism.
- **OAuth 2.1 delegated authorization + token exchange (RFC 8693)** — scoped, narrowed tokens for "what may this agent do, on whose behalf," including MCP's mandatory OAuth 2.1 profile since June 2025.
- **Cross-App Access / Identity Assertion Authorization Grant** — an emerging IETF mechanism for enterprise brokering of agent delegation across applications.
- **Guardrail classifiers (content-safety models)** — a purpose-trained model (e.g., Llama Guard 4, 12B, natively multimodal, Dec 2025) that classifies inputs/outputs as safe or unsafe against a hazard taxonomy; used as a fast, self-hosted single-verdict check on content safety.
- **Programmable guardrail frameworks** — runtime orchestration (e.g., NVIDIA NeMo Guardrails, Apache-2.0, using the Colang DSL) that routes requests through configurable input, dialog, retrieval, execution, and output rails; used when moderation is a multi-check, stateful pipeline rather than a single classification.
- **Output-validation libraries** — structured, schema-plus-content validators with auto-correction loops (e.g., Guardrails AI) drawn from a hub of pre-built checks; used when the problem is making output conform to both structure and content policy simultaneously.
- **Layered guardrail architecture** — combining input validation, dialog rails, output filtering (PII redaction, hallucination checks), tool-call/execution gating, and a managed moderation API as a final probabilistic check, mapped to OWASP LLM Top 10 categories; the converged 2026 reference architecture rather than any single tool.

### 4. Concrete Examples
The postmark-mcp npm package shipped fifteen clean versions to build trust before version 1.0.16 silently BCC'd every processed email to an attacker address — the first confirmed real-world malicious MCP server, disclosed by Koi Security in September 2025. CVE-2025-6514, a CVSS 9.6 OS command injection in the widely-used `mcp-remote` package, affected over 437,000 downloaded environments. OX Security's April 2026 "Mother of All AI Supply Chains" disclosure found a systemic, by-design command-execution flaw in Anthropic's official MCP SDKs (Python, TypeScript, Java, Rust), affecting an estimated 200,000 instances across 150 million package downloads. On the identity side, the IETF Internet-Draft `draft-klrc-aiagent-auth-00` (March 2026) composes WIMSE, SPIFFE, and OAuth 2.0 into a dual-identity access token carrying both the agent's workload identity (`client_id`) and the delegated user (`sub`). Microsoft, Okta, and Auth0 shipped agent-native IAM products (e.g., Entra Agent ID) in the past year. On the guardrails front, Llama Guard 4 scores 0.737 F1 on the OpenAI Moderation benchmark and 0.961 on HarmBench but degrades on long-context traces (0.602 F1, 0.516 false-positive rate), illustrating that no single classifier is uniformly reliable across content types. NeMo Guardrails ships built-in jailbreak heuristics, self-check moderation, Microsoft Presidio PII detection, and Llama Guard integration as composable rails.

### 5. Anti-Patterns & Failure Modes
No single control reliably prevents prompt injection across all documented variants — OWASP itself states the risk cannot be fully eliminated, so relying on any one filter as a complete defense is a documented failure mode; defense-in-depth is the converging guidance. Auto-approving MCP server updates or tool description changes without re-review enables "rug pull" attacks where a legitimate-seeming tool later turns malicious. Leaving MCP servers unauthenticated is common in the wild: a July 2025 scan found at least 1,862 publicly accessible, unauthenticated MCP instances, and only about 8.5% of scanned public servers use OAuth. Retaining persistent agent memory features that aren't business-required expands the exploitable persistence surface for successful injections. There is currently no ratified, single standard for agent identity — as of August 2026 the IETF's own position is that agents need no new protocol, only correct composition of existing ones — so any vendor claiming a definitive "agent identity standard" should be treated skeptically. Relying on a single guardrail classifier as a complete safety solution is itself an anti-pattern: Guardrails AI is explicitly not a security guardrail (no injection detection), and a content-safety model tuned for short exchanges can silently fail on long agentic traces, so production systems need the layered rail architecture rather than one tool.

### 6. State of Practice
MCP security is an acute, fast-moving crisis as of 2026: independent scans find 30-82% of public MCP servers carry exploitable flaws (path traversal in 82% of file-operation servers per Endor Labs, command-injection risk in 34%), and 14+ CVEs were assigned to MCP implementations by July 2026, including the critical DuneSlide pair (CVSS 9.8). This is squarely a live, rapidly-evolving 2025-2026 problem, not settled practice — flag any pre-2025 MCP security guidance as likely outdated. Agent identity standardization is similarly immature: WIMSE remains a family of IETF drafts with no finished RFC, and governance frameworks (CSA Agentic Trust Framework, February 2026; NIST's NCCoE agent identity project) are arriving faster than the underlying protocols.

## AREA 8 — PRODUCTION OBSERVABILITY & DRIFT MONITORING

**Candidate assessment and evals-vs-observability verdict:** Surveying 2025-2026 practitioner material across vendor engineering blogs (Arize, Langfuse, LangSmith, Braintrust, Future AGI), buyer's guides, and production checklists, observability is increasingly treated as a distinct discipline layered on top of evals rather than a subsection of them — though the boundary remains actively contested in commercial positioning. Multiple 2026 sources explicitly decompose the stack into three layers — tracing ("what is this thing actually doing"), eval runs ("is it good enough," typically pre-deploy/CI-gated), and drift detection ("is it still good enough," continuous production monitoring) — and call it a common mistake to ship tracing alone and label it observability. Vendors like Arize (Phoenix) and Langfuse market observability as a superset that folds in span-attached evals plus drift/embedding analysis unique to live traffic, capabilities that CI-first eval tools (Promptfoo, DeepEval) do not natively provide. At the same time, most leading platforms (Langfuse, LangSmith, Braintrust, Arize Phoenix) bundle tracing and evaluation into one product, and industry write-ups frequently use "evals and observability" as a single compound category rather than two cleanly separated markets. The practical verdict: observability is functionally a superset containing eval-scoring as one of its three constituent layers, with production drift detection and full-trace debugging as the genuinely distinct capabilities evals alone do not deliver — this justifies treating it as its own pattern area rather than folding it into Area 4. Weighed against the other candidates, observability edges out model routing/token economics (a real gap but narrower and largely a sub-concern of cost, already touched on across other areas), fine-tuning-vs-prompting (a single technique decision, not a load-bearing discipline — later given its own Area 9), human-in-the-loop/UX (partially covered under Area 7's approval gates), and deployment/versioning (a DevOps concern with less distinct 2025-2026 practitioner literature). Observability is recommended as AREA 8 because it has the deepest, most dedicated 2025-2026 literature, its own maturity curve (tracing → eval-coupling → drift detection), a large and consolidating vendor landscape, and clear failure modes distinct from anything already catalogued.

### 1. Definition
Production observability is the practice of capturing, storing, and analyzing the full runtime execution of LLM/agent systems — every prompt, model response, tool call, retrieval, token count, latency, and cost — as structured traces, then continuously monitoring that live traffic for quality drift, distribution shift, and failure patterns. It is distinct from evals (Area 4) in temporal scope and object of measurement: evals are typically point-in-time, dataset-driven quality checks run before or at deploy time against known test cases, while observability is the continuous, trace-native discipline of watching real, uncurated production traffic and detecting when behavior — model, prompt, or input distribution — has silently changed.

### 2. Routing Triggers
Reach for observability once an agent runs autonomously across multiple steps or sessions such that a failure cannot be reproduced or debugged from logs alone — this is described as the "day-2 problem" of agent engineering. It is also the right pattern whenever a team needs to attribute cost, latency, or quality issues to a specific step in a multi-step pipeline, or when a static eval suite has passed but real users are reporting degraded quality, signaling that production-input distribution has diverged from the eval dataset.

### 3. Technique Taxonomy
- **Distributed tracing / spans** — capturing each LLM call, tool invocation, and retrieval step as a named span with model, tokens, latency, and cost attached, typically via OpenTelemetry GenAI semantic conventions; used as the foundational instrumentation layer for any production LLM system.
- **Span-attached online evals** — running LLM-as-judge or rubric scorers on a sampled slice (commonly 5-20%, plus 100% of errors) of live production traces and attaching scores as span attributes; used to bridge offline eval quality with real traffic.
- **Golden-set replay** — scheduled replay of a curated set of 50-500 reference traces through the current production pipeline to catch regressions from silent provider-side model updates, prompt edits, or tool schema changes; the most-cited reliable drift signal in 2026 sources.
- **Drift detection (multiple sub-types)** — statistical monitoring split into distinct sub-problems: input-distribution drift, retrieval-corpus drift, prompt drift, judge-calibration drift, and agent-step drift, each requiring a different detection method and tool.
- **Cost/latency attribution** — per-request, per-tenant, per-feature tagging of token spend and latency so cost anomalies (e.g., a 5x spike) trigger alerts independent of quality metrics.
- **Context/session fingerprinting** — logging a hash or structured snapshot of the active context (instructions, tools, constraints) at each turn so that behavior divergence can be traced back to a specific context-state change.
- **Tiered trace storage** — hot (full trace, days), warm (span summaries, months), cold (metadata/cost only, indefinite) retention policies for long-running agents where full-fidelity retention is cost-prohibitive.
- **Alerting policy tiers** — page-worthy (golden-set score drop 2+ consecutive runs, error rate 3x baseline, cost spike 5x), ticket-worthy (gradual 7-day drift, latency growth), and dashboard-only (trend lines) severity bands; used to avoid alert fatigue from noisy raw metrics.

### 4. Concrete Examples
Langfuse is the leading open-source, OpenTelemetry-native platform (MIT-licensed core) offering deep self-hosted trace capture, prompt management, and CI-integrated evals, commonly cited as the fastest first integration (roughly 30 minutes) for a team instrumenting a production agent for the first time. LangSmith remains the deepest-integrated option for LangChain/LangGraph runtimes, with native graph semantics and zero-friction capture for that ecosystem. Arize Phoenix, built on the team's prior ML-observability heritage, is consistently ranked strongest for drift detection and embedding analysis, shipping a built-in hallucination detector and OpenInference-native tracing. Future AGI, Evidently, WhyLabs, and Fiddler are named as specialized drift-detection tools, each targeting a different drift sub-type (retrieval-corpus, tabular-feature, agentic execution-lineage, respectively). By April 2026 the agent-observability field had consolidated to roughly six production-grade platforms — LangSmith, Langfuse, Arize Phoenix, Helicone, Datadog LLM Observability, and Honeycomb LLM Observability — with practitioner guidance to pair the LLM-specific platform with whole-stack APM (Datadog, Honeycomb) since the two operate at different layers.

### 5. Anti-Patterns & Failure Modes
Shipping tracing (span capture) alone and calling it "observability" is explicitly named as the most common mistake — it shows what happened but not whether the system is still working correctly, since it lacks the eval-scoring and drift layers. Running only a static, pre-deploy golden-set eval without continuous production-side scoring misses real-world distribution shift and slow drift that fixed test sets never surface, since golden-set replay and live-traffic scoring catch different failure classes (fixed-reference regression vs. distribution shift). Treating "drift" as a single undifferentiated phenomenon rather than five distinct sub-types (input, retrieval-corpus, prompt, judge-calibration, agent-step) leads teams to buy or build the wrong detection tool for their actual failure mode. Under-provisioning trace retention for long-running autonomous agents (standard 1-7 day retention) leaves teams unable to debug incidents discovered after the fact; tiered storage is the corrective pattern. Poorly calibrated alert thresholds that fire on ordinary noise get muted by on-call teams, defeating the purpose of drift alerting — thresholds must be tuned against historical noise before going live.

### 6. State of Practice
This is a rapidly maturing but still-consolidating category as of 2026: what "used to mean 'did the prompt and response get logged somewhere'" is now described as an architectural decision spanning OTel-native versus proprietary span formats, eval-decoupled versus eval-coupled design, and multi-modal support. The OpenTelemetry GenAI semantic-convention effort and a maturing tail-sampling processor in the OTel collector (2026) are cited as significant infrastructure developments that moved outcome-aware sampling to off-the-shelf tooling. EU AI Act enforcement entering its active phase in 2026 has pushed audit-trail and PII-redaction requirements from advisory guidance to compliance mandate, a notable regulatory driver behind observability adoption. The evals-vs-observability boundary is explicitly flagged here as contested rather than settled: some practitioner sources treat them as one combined "evals and observability" market category, while others insist on a strict three-layer separation — this catalog treats observability as the superset discipline per the majority of 2026 architectural write-ups, but notes the terminology is not yet standardized industry-wide.

## AREA 9 — MODEL ADAPTATION: PROMPTING vs RAG vs FINE-TUNING

**Definition and terminology:** The commonly adopted umbrella term for this decision space is **model adaptation** (also "LLM adaptation techniques") — the practice of adjusting a pre-trained foundation model's outputs for a specific use case. Within that umbrella, practitioner and academic literature converges on a clean distinction: **knowledge injection** (getting the model to know new or current facts) versus **behavior shaping** (getting the model to consistently act, format, or reason a certain way). Meta's Llama 3 research explicitly separated these two use cases and found fine-tuning weak for knowledge injection relative to RAG, while remaining the right tool for behavior. A newer academic six-dimensional taxonomy (arXiv, Aug 2026) proposes "post-training adaptation" as the more precise umbrella for weight-modifying techniques specifically, situating fine-tuning, PEFT, alignment, and retrieval augmentation as siblings under it — but "model adaptation" remains the dominant term in day-to-day practitioner writing.

### 1. Definition
Model adaptation is the set of three competing techniques — prompting, retrieval-augmented generation (RAG), and fine-tuning — for shaping what a pre-trained LLM knows or how it behaves, without necessarily retraining from scratch. The three sit on two independent axes: prompting and RAG operate at inference time and never touch model weights, while fine-tuning modifies the weights themselves; separately, RAG and prompting are aimed primarily at knowledge (what the model knows), while fine-tuning is aimed primarily at behavior (how the model acts by default).

### 2. Routing Triggers
Start with prompting for any new task or early-stage product — it is the default, zero-infrastructure option and, per the Applied LLMs practitioner collective's recommended sequence, the first thing to exhaust before reaching for anything else. Escalate to RAG when the model's failures trace to missing or outdated knowledge (proprietary data, recent events, frequently changing documents) that would be expensive or impossible to bake into weights. Escalate to fine-tuning only when prompting (with few-shot examples) has been tried and failed on a narrow, high-volume, well-defined task where the problem is demonstrably about *behavior* — output format, tone, domain vocabulary, or a reasoning pattern the model can't reliably hold — not about missing facts.

### 3. Technique Taxonomy
- **Zero-/few-shot prompting** — steering behavior via instructions and 3-5 in-context examples with no infrastructure; used as the first attempt for any new task.
- **Retrieval-augmented generation (RAG)** — injecting retrieved, source-attributable documents into the prompt at query time; used when knowledge is dynamic, must be cited, or is too large to fit in weights.
- **Full fine-tuning (SFT)** — updating all model weights on a labeled task-specific dataset; used for the largest behavior shift but is the most compute- and data-intensive route, and carries the highest catastrophic-forgetting risk.
- **LoRA (Low-Rank Adaptation)** — freezes the base model and trains small low-rank matrices injected into attention/MLP layers, updating roughly 0.1-1% of parameters while recovering 90-95% of full fine-tuning quality; the 2026 default for teams with adequate GPU memory.
- **QLoRA** — combines 4-bit (NF4) quantization of the frozen base model with LoRA adapters trained in 16-bit, cutting VRAM needs by roughly 75% at a small quality cost (80-93% of full fine-tuning); the standard entry point for consumer-GPU or budget-constrained fine-tuning in 2026.
- **DoRA (Weight-Decomposed LoRA)** — decomposes the weight update into magnitude and direction components, often matching full fine-tuning quality at the same rank as LoRA; increasingly paired with QLoRA as the 2026 default combination.
- **Preference optimization (DPO/RLHF/GRPO)** — post-SFT alignment step that shapes stylistic or safety preferences using preference pairs or verifiable rewards, not new facts; used to polish behavior after base fine-tuning, and described as "behavioral shaping, not knowledge injection."
- **Continued pre-training (CPT) / domain adaptation** — further pretraining on large volumes of raw domain text before task-specific tuning, used to build deep terminology/semantic grounding in high-stakes domains (legal, medical, finance) before SFT.
- **Distillation** — training a smaller "student" model to mimic a larger "teacher" model's outputs, used for cost/latency reduction at serving time rather than for adding new knowledge or behavior per se.
- **Hybrid fine-tune + RAG** — fine-tuning the model for stable behavior (format, tone, policy) while layering RAG on top for volatile, citable facts; described as the 2026 production consensus rather than a fallback.

### 4. Concrete Examples
The Applied LLMs practitioner collective (Eugene Yan, Hamel Husain, Jason Liu, and colleagues) codifies a widely cited four-step escalation order: prompt engineering first, add RAG if the model lacks knowledge, add fine-tuning only if the model lacks behavior, then go hybrid for high-stakes production systems like legal or medical assistants. QLoRA (Dettmers et al., May 2023) remains the foundational technique enabling 65B-parameter fine-tuning on a single 48GB GPU while preserving full 16-bit fine-tuning performance, and by 2026 is described as production-ready with mature tooling (Unsloth, Axolotl, Hugging Face PEFT). Cost data from 2026 sources shows an 8B model full fine-tune at $80-150 versus QLoRA at $5-10, illustrating the economic driver behind PEFT adoption. A February 2026 PMC systematic review catalogs multiple production hybrid FT+RAG systems in medicine, including a Dual Federated RAG and a Federated Knowledge Graph approach, evidencing real deployed hybrids rather than only theoretical framing. Databricks' engineering blog documents LoRA outperforming full fine-tuning in some cases specifically because it avoids catastrophic forgetting, a counterintuitive but now well-established production finding.

### 5. Anti-Patterns & Failure Modes
Using fine-tuning to inject new factual knowledge is the most commonly cited anti-pattern — fine-tuning is documented across multiple 2025-2026 sources as a comparatively weak and expensive way to teach facts versus simply retrieving them via RAG. Reaching for fine-tuning before exhausting prompting and few-shot examples wastes the one-time setup cost on a problem prompting could have solved; multiple practitioner decision frameworks recommend a hard gate (e.g., "have you tried a detailed system prompt with 3-5 few-shot examples and it's still inconsistent?") before considering fine-tuning at all. Full fine-tuning risks catastrophic forgetting — degrading the base model's general capabilities while specializing it — which is a key reason LoRA/QLoRA have become the 2026 default over full-parameter updates. Fine-tuning on stale, static data without a refresh plan means the baked-in knowledge snapshot silently ages; unlike RAG, correcting this requires a full re-fine-tune rather than a document update. Committing to fine-tuning at low inference volume (under roughly $1,000-10,000/month spend, per multiple 2026 cost-threshold frameworks) rarely pays back the setup investment, since prompting remains cheaper until volume is high enough to amortize training cost.

### 6. State of Practice
Parameter-efficient fine-tuning (PEFT) — LoRA and QLoRA specifically — is described as the mature, production-ready default for the vast majority of 2026 fine-tuning work, with full-parameter fine-tuning reserved for cases demanding maximum quality or where PEFT demonstrably underfits. The field has converged on a consistent decision heuristic across at least a dozen independently published 2026 frameworks: default to prompting, add RAG for facts, reserve fine-tuning for behavior, and combine fine-tuning with RAG for high-stakes hybrid systems — this represents unusually strong practitioner consensus compared to other areas in this catalog. DoRA and QLoRA-plus-DoRA are cited as the emerging 2026 default combination for new fine-tuning projects, an incremental but real development since 2025. One area of active academic contestation: a 2026 arXiv paper on distilled pretraining finds that distillation improves test-time scaling but can impair in-context learning through the same underlying mechanism — a nuance not yet reflected in most practitioner-facing guidance and worth flagging as an open research question.
